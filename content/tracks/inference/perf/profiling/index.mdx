<Section kind="intuition" title="A stopwatch that lies">

Timing a model looks easy: read the clock, call the model, read the clock again. Done naively, every part of that
can mislead. The first call includes one-time setup that no later call pays. On a GPU the call returns before the
work is finished, so the clock measures how fast Python handed work over. A handful of calls cannot show the rare
slow ones users complain about. And a load test that waits politely for each reply never sends the requests that
would have piled up behind a freeze.

This lesson builds a benchmark that avoids each trap, then uses a profiler to find where a request's time and
memory actually go. The rule throughout: measure before optimizing, and know what your measurement measured.

</Section>

<Section kind="technical" title="What to measure and how">

**Latency** is the time for one request; **throughput** is requests (or items) per second. Report latency as
<Term id="latency-percentile">percentiles</Term>: p50 is the median, p99 the time only 1% of requests exceed. The
mean is useful for capacity math but hides the tail, because one 900 ms call among 200 calls of 12 ms moves the
mean by $900 / 200 = 4.5$ ms while the median barely changes.

A sound benchmark has four parts:

1. <Term id="warm-up">Warm-up</Term>: run untimed calls first. The first GPU call creates the CUDA context, loads
   and selects kernels, and grows the memory allocator's pool; compilers such as `torch.compile` or TensorRT do
   even more work on the first call. A long-running server pays this once.
2. **Synchronization**: GPU kernels are queued and run asynchronously. Call `torch.cuda.synchronize()` (or copy the
   result to the CPU) before reading the clock, or use CUDA events.
3. **Enough samples**: estimating p99 needs well over 100 calls; hundreds to thousands is better. Repeat the whole
   run, since results drift with clock speeds, temperature and neighbors on shared machines.
4. **Fixed conditions**: the same batch size, input shapes, precision and hardware you will deploy, recorded next
   to the result.

**Throughput under load** needs a load generator, and its design matters. A *closed-loop* client sends the next
request only after the previous reply arrives. If the server freezes, the client stops sending, so it records one
slow request instead of the dozens real users would have sent meanwhile. That is
<Term id="coordinated-omission">coordinated omission</Term>. An *open-loop* client sends on a schedule regardless of
replies, like independent users, and measures each request from when it should have been sent.

**Where the time goes** comes from a <Term id="profiler">profiler</Term>. Time each stage of the request
(parsing, preprocessing, host-to-device copy, model, postprocessing, serialization) before profiling the model
itself. Amdahl's law sets the ceiling: speeding up a part that takes a fraction $f$ of the time by a factor $s$
gives an overall speed-up of $1 / ((1 - f) + f / s)$, never more than $1 / (1 - f)$.

**Peak memory** decides whether a batch fits. Measure it (`tracemalloc` for NumPy on the CPU,
`torch.cuda.max_memory_allocated()` on a GPU) and compare it with your estimate from the
[memory lesson](#/learn/inference/memory/memory-estimation); a gap points to a temporary you forgot.

<Section kind="mistakes" title="Benchmarking mistakes">

<CommonMistake
  title="Timing GPU work without synchronizing"
  wrong={'t0 = time.perf_counter()\ny = model(x)\nprint(time.perf_counter() - t0)   # 0.25 ms?'}
  error="No error. The number is the time to queue kernels, not to run them."
  cause="CUDA calls return as soon as the work is queued. The next operation that needs the result (or a synchronize) waits."
  fix={'t0 = time.perf_counter()\ny = model(x)\ntorch.cuda.synchronize()\nprint(time.perf_counter() - t0)'}
/>

<CommonMistake
  title="Including the first call"
  wrong={'times = [timed(model, x) for _ in range(200)]   # the first call creates the CUDA context'}
  error="No error. The mean and max are inflated by one-time setup that a running server never pays again."
  cause="The first calls initialize the device, select kernels, compile graphs and grow memory pools."
  fix={'for _ in range(10):\n    model(x)            # warm-up, untimed\ntimes = [timed(model, x) for _ in range(200)]'}
/>

<Callout kind="warning">
  Do not benchmark with a closed-loop client and call the result a user-facing latency. Use an open-loop generator
  at a fixed arrival rate (Locust and k6 can do this with constant-arrival settings; wrk2 does it by design), and
  report the rate along with the percentiles.
</Callout>

<Callout kind="warning">
  A benchmark on random inputs can be wrong for models whose cost depends on the data: language models stop
  generating at different lengths, and detection models postprocess more boxes on busy images. Benchmark on a
  sample of real requests.
</Callout>

</Section>

<Section kind="practice" title="A benchmark checklist">

1. **Write down the question** first: "p99 at 200 requests per second on one L4", not "is it fast".
2. **Record the setup** with each result: hardware, driver and library versions, batch size, input shapes,
   precision, and the commit of the model.
3. **Warm up, synchronize, and take enough samples**; report p50, p95, p99, max and throughput, not only the mean.
4. **Break the request into stages** before optimizing anything, and profile the slowest stage.
5. **Load test open-loop** at several arrival rates up to and beyond the expected peak.
6. **Measure peak memory** at the largest batch you will allow, and keep headroom for fragmentation.
7. **Repeat runs** and compare distributions; treat differences smaller than run-to-run noise as no difference.

</Section>

<Section kind="summary">

- Report latency as percentiles from hundreds to thousands of calls; the mean hides the tail.
- Warm up before timing and synchronize GPU work before reading the clock.
- Closed-loop load tests hide freezes (coordinated omission); use an open-loop generator at a stated rate.
- Time each stage of a request before optimizing the model: here JSON parsing took 80% of the time.
- Measure peak memory and compare it with an estimate; a gap points to a forgotten temporary.
