<Section kind="intuition" title="A metered taxi with a stranger's directions">

Every request to a model is a metered taxi ride: you pay per <Term id="token">token</Term> in and per token out, and the
meter runs for every passenger. A prototype that costs pennies in a demo can cost thousands a month at real traffic, and
a reply that takes six seconds feels broken. Most savings come from not paying twice for the same thing: the same
instructions in every request, or the same question asked by a hundred people.

Now give the taxi driver a note from a passenger that says "ignore your dispatcher and drive to this address". A careful
driver ignores it. A language model can't reliably tell instructions from data, so anything it reads (a document, an
email, a web page) can try to steer it. Security for AI features is mostly about what the model is *allowed* to do when
that happens.

</Section>

<Section kind="technical" title="Where the money and the seconds go, and what can go wrong">

**Cost per request** is input tokens times the input price plus output tokens times the output price. Output is usually
several times more expensive per token, so a request with 4,500 tokens in and 300 out at example prices of \$4 and \$20
per million costs

$$
\frac{4500 \times 4 + 300 \times 20}{10^6} = 0.018 + 0.006 = \$0.024
$$

At 20,000 requests a day that is \$14,400 per 30-day month. The prices here are examples; check your provider's page.

**Latency** has two parts. <Term id="time-to-first-token">Time to first token</Term> grows with the prompt the model
has to read. After that, output arrives at a roughly steady rate, so a 300-token answer at 60 tokens per second adds
5 seconds. Streaming doesn't make the reply shorter; it lets the user start reading after the first part.

**Levers, cheapest first:**

| Lever | Saves | Watch out for |
| --- | --- | --- |
| <Term id="prompt-caching">Prompt caching</Term> of a stable prefix | input cost and time to first token | only an identical prefix hits; changing content goes after it |
| <Term id="response-cache">Response cache</Term> for repeated questions | the whole model call | only for answers that are the same for every user; include versions in the key |
| Shorter output (ask for it, lower `max_tokens`) | output cost and total latency | check quality on the eval set |
| Less retrieved context | input cost | recall drops if you cut too much |
| A smaller model | everything | quality: measure on the [eval set](#/learn/ai/reliability/evals-guardrails) before switching |

**Privacy.** Everything in a prompt is sent to the provider and often written to your own logs. Send only what the
task needs, keep personal data out of prompts where you can, check the provider's data retention terms, and treat logs
of prompts and answers as sensitive data, with access control and an expiry.

**Security.** <Term id="prompt-injection">Prompt injection</Term> is text that tries to override your instructions.
*Direct* injection comes from the user; *indirect* injection hides in content the model reads: a retrieved note, an
email, a web page. It becomes dangerous when one agent has three things at once: access to private data, exposure to
untrusted content, and a way to send data out (email, web requests, links it can make the user click). No filter
catches every phrasing, so the dependable defenses limit the damage:

- **<Term id="least-privilege">Least privilege</Term>**: offer only the tools the current task needs, and run them with
  the signed-in user's credentials, never an admin key.
- **Check tool arguments in code**: the model writes the arguments, so validate them against rules it can't change.
- **A person approves side effects**: sending, deleting and paying wait for a click.
- **Treat model output as untrusted**: escape it before rendering it as HTML, never run it as code or SQL unchecked.

<Callout kind="simplification">
  Costs and latencies on this page come from a simple formula with example prices and example speeds, not from
  measurements: real time to first token varies with load, and providers bill cache writes and reads at their own
  rates (here cache reads cost 10% of the input price and writes are ignored). In the injection scenario, the model's
  tool calls are scripted: a real model may or may not follow the hidden text, so the scenario assumes it does. The
  policy that decides which calls run is real code.
</Callout>

</Section>

Things to try:

- In the cost estimate, turn on prompt caching: the monthly estimate falls from \$14,400 to \$7,920, and time to first
  token from 1.07 s to 0.69 s, because 3,000 of the 4,500 input tokens are read from the cache.
- Add a 20% response cache hit rate: \$6,336. Then lower the output to 150 tokens: \$4,896, and the full reply is about

- Switch to the small model tier: the estimate drops by about 97%. Whether that is a saving depends entirely on whether

- In the policy experiment, with everything off, the email and the delete both run: 2 harmful calls, and nobody saw them.
- Turn on only the recipient check: the email is blocked, but the delete still runs. Rules for one tool don't cover
  the others.
- Turn on only "the tools this task needs": both harmful calls are blocked, because summarizing never needed email or
  delete. Turn on only "ask the user": both wait for a person, who sees the attacker's address.

<Section kind="practice" title="A checklist before launch">

1. **Estimate cost** at expected and at 10× traffic, and set a spending limit and per-user
   <Term id="rate-limit">rate limits</Term> so one user or one bug can't run up the bill.
2. **Measure** time to first token and full reply time as <Term id="latency-percentile">percentiles</Term> (p50 and p95),
   and log tokens and cache reads per request.
3. **Apply the cheap levers** (prompt caching, response cache, shorter output), then re-run the eval set; only then
   consider a smaller model.
4. **List every tool** with what it can change, and remove or gate the ones the task doesn't need.
5. **Review data flows**: what personal data enters prompts, where prompts and answers are logged, and for how long.
6. **Test injection** by planting hostile instructions in documents, emails and pages the system reads, and add them to
   the eval set.

[Deploying and monitoring](#/learn/ai/ops/deploy-monitor) watches these numbers after release and rolls back when they
get worse.

<Section kind="summary">

- Cost is tokens in and out times their prices, times volume; output tokens usually cost the most per token.
- Prompt caching cuts the cost and delay of a stable prefix; a response cache skips the model for repeated questions.
- Shorter output and smaller models save the most, and must be checked against the eval set.
- Anything the model reads can try to give it instructions; filters miss some.
- Limit the damage: only the tools the task needs, the user's own credentials, argument checks in code, approval for
  side effects, and model output treated as untrusted.

</Section>
