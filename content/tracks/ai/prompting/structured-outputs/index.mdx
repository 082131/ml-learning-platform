<Section kind="intuition" title="A form, not a letter">

If you ask a new colleague to "sort these support emails", you get back a letter: helpful, readable, and different
every time. If you hand them a form with four boxes, a list of allowed categories and one filled-in example, you get
back something you can put in a spreadsheet.

Prompts work the same way. A prompt is the whole briefing: who the model is working for, what the rules are, what the
answer must look like, and an example. When code consumes the answer, ask for a
<Term id="structured-output">structured output</Term>, check it like you would check any untrusted input, and have a
plan for when it is wrong.

</Section>

<Section kind="technical" title="Prompt parts, schemas and validation">

**A prompt has parts.** The <Term id="system-prompt">system prompt</Term> holds what stays the same: the role, the
definitions, the rules and the output format. The user message holds what changes: here, the ticket. Adding a worked
example is <Term id="few-shot-prompting">few-shot prompting</Term>; it is often the quickest fix for a format or a
borderline case, and it costs input tokens on every request.

**A schema says what valid means.** A <Term id="json-schema">JSON Schema</Term> lists the types, the required keys,
the allowed values and the limits. For a Lumen ticket:

| Key | Type | Rule |
| --- | --- | --- |
| `category` | string | one of billing, sync, account, api, other |
| `urgency` | integer | 1, 2 or 3 |
| `summary` | string | at most 80 characters |
| `needs_human` | boolean | required |

No other keys are allowed.

**Getting JSON back.** Some APIs can constrain generation to a schema, so the reply is always well-formed JSON of that
shape. Otherwise you ask for JSON in the prompt and the model usually, not always, complies. Either way the reply can be
cut off by `max_tokens`, and a schema can't express every business rule.

**Validate, then use, retry or fall back.**

1. Parse with a strict JSON parser. Unwrap a known wrapper (a ```` ```json ```` fence) if you choose to, but never
   guess where JSON starts inside prose.
2. Validate against the schema. Collect every error with its path, such as `$.urgency: expected integer, got string`.
3. On failure, send the errors back once and ask for corrected JSON. If that fails too, fall back: a default, a human
   queue, or a clear error.

**Compare prompts on a set, not an example.** One ticket tells you almost nothing. Score each prompt variant on a few
dozen labeled examples and count the outcomes: correct, wrong value, invalid.

  The model replies on this page are scripted to show the failure kinds you meet in practice; they are labeled. The

</Callout>

</Section>

<Section kind="practice" title="Prompts as code">

Treat prompts like code: keep them in version control, give each a version name, and log which version produced each
output. Keep a labeled set of real inputs (start with 30 to 50) and re-score it whenever the prompt or the model changes.
When a prompt fails, add the failing input to the set before fixing it, so it stays fixed.

The [evaluation lesson](#/learn/ai/reliability/evals-guardrails) grows this into a full evaluation set with graders,
and [RAG](#/learn/ai/rag/rag-pipeline) uses the same prompt structure with retrieved documents as the context.

</Section>

<Section kind="summary">

- A prompt is a briefing: role, definitions, rules, output format and an example.
- Ask for structured output when code consumes the answer, and describe it with a JSON Schema.
- Parse strictly, validate against the schema, retry once with the errors, then fall back.
- Even schema-constrained output can be cut off and can hold wrong values.
- Compare prompts by scoring them on a labeled set, never on one example.
