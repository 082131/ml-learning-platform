<Section kind="intuition" title="When Git has to ask you">

A three-way merge compares each branch with the merge base and takes every change from the side that made it.
That works as long as the two branches changed different parts of a file. When both changed the **same** lines in
different ways, there is no rule that could pick the right answer: one person lowered the learning rate, the other
raised it. Git does not guess. It writes both versions into the file, marks them, and stops so that a person can
decide.

That is a <Term id="merge-conflict">merge conflict</Term>. It is not an error and nothing is lost: the merge is
paused, half done. You finish it by writing the file you want, or call it off with `--abort`.

</Section>

<Section kind="technical" title="How conflicts are found and shown">

Git diffs the base against each side and lines the changed regions up:

| Since the merge base | Result |
| -------------------- | ------ |
| Region changed on one side only | Take that side's version |
| Changed identically on both sides | Take it once |
| Changed differently on both sides, or the changes touch (adjacent lines) | Conflict |
| File deleted on one side, modified on the other | Conflict (modify/delete) |

For a content conflict, Git writes <Term id="conflict-markers">conflict markers</Term> into the working tree file
and records three versions in the index (stages 1, 2, 3: base, ours, theirs). `git status` shows the file as
`UU` (both modified). The operation stays in progress until you `git add` every conflicted file and run
`git commit` (for a merge) or `git rebase --continue` / `git cherry-pick --continue`.

"Ours" and "theirs" depend on the operation:

| Operation | `HEAD` / ours | theirs |
| --------- | ------------- | ------ |
| `git merge feature` on main | main | feature |
| `git rebase main` on feature | main, plus your commits replayed so far | the commit of yours being replayed |
| `git cherry-pick X` | the current branch | commit X |

</Section>

<CommonMistake

<Section kind="practice" title="Fewer, smaller conflicts">

- **Merge or rebase from `main` often.** A conflict with one day of changes is small; one with a month is a
  project.
- **Keep pull requests small and short-lived.**
- **Set `merge.conflictStyle zdiff3`** so you always see the base.
- **Never hand-merge generated files** (lock files, compiled outputs): take one side and regenerate
  (`uv lock`, `npm install`).
- **One setting per line in configs**, sorted where order does not matter, so unrelated edits do not touch.
- **Run the tests after resolving.** A merge without textual conflicts can still be wrong, for example when one
  branch renames a function the other starts calling.

</Section>

<Section kind="summary">

- Git conflicts when both sides changed the same or touching lines since the merge base. Everything else merges
  automatically.
- Markers show ours (HEAD) and theirs; zdiff3 adds the base. In a rebase, ours is the branch you replay onto.
- Resolve by editing, then `git add` and `git commit` (or `--continue`). `--abort` undoes the whole attempt.
- `git add` does not check for leftover markers: search for them and run the tests.

</Section>
