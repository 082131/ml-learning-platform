<Section kind="intuition" title="One feature, start to finish">

Each lesson in this track covered one piece: commits, branches, merging, remotes, pull requests, CI, versions,
documentation. In a team they are one routine, repeated for every change. This capstone runs it end to end on a
small ML repository: add an evaluation feature on a branch, get it reviewed and tested, merge it with its
documentation, and publish version 1.1.0 with a changelog and a tag.

When you can do this without looking anything up, you can work in almost any team's repository.

</Section>

</Section>

<Section kind="mistakes" title="Where this goes wrong">

<CommonMistake
  title="Tagging before the merge"
  wrong={'git switch feat/evaluate\ngit tag -a v1.1.0 -m "Add evaluate()"\ngit push origin v1.1.0'}
  error="(no error) after a squash merge, the tagged commit is not in main; git describe on main still says v1.0.0-1-g..."
  cause="The tag names the branch commit, which squash merging replaced with a new one."
  fix="Merge first, git pull on main, then tag the commit main points to."
/>

<CommonMistake
  title="Releasing with a red or skipped CI"
  wrong={'# required checks were "still running"; an admin bypassed protection to merge'}
  error="(next day) ImportError: cannot import name 'evaluate' from 'churn_model' (in the published package)"
  cause="The release was cut from a commit nobody had tested."
  fix="Do not bypass protection for releases. Wait for green checks on the exact commit you tag."
/>

<CommonMistake
  title="Forgetting the version string in the package"
  wrong={'git tag -a v1.1.0 -m "..."   # pyproject.toml still says version = "1.0.0"'}
  error={'$ pip show churn-model\nVersion: 1.0.0'}
  cause="The tag and the package metadata disagree."
  fix="Bump the version in the release PR, or derive it from the tag (setuptools-scm, hatch-vcs) so there is one source."
/>

<Section kind="summary">

- The team routine: branch, commit (Conventional Commits), document in the same PR, rebase, push, review with
  required CI, merge, release.
- The version comes from the commits; the changelog is written for users; the annotated tag goes on the merged
  commit in `main`.
- Protection rules and CI make the routine enforceable, not just recommended.
- With code, data pointers, docs and tags all in Git, any release can be rebuilt and explained later.

You have finished the Git, GitHub and Documentation track. The certification exam tests all of it, including a
hands-on part.

</Section>
