<Section kind="intuition" title="A recipe, a parts list, or a boxed kit">

You can hand someone a model in three ways. A **parts list** names every weight and its numbers, but you need
the original Python code to know how to wire them together: that is a PyTorch
<Term id="checkpoint">checkpoint</Term> or a <Term id="safetensors">safetensors</Term> file. A **recipe** writes
down every step of the computation as well, so any kitchen can cook it without the original cook: that is an
<Term id="onnx">ONNX</Term> file. A **boxed kit** puts the parts, the assembly settings and even the
dictionary for reading the input into one sealed box, ready for one particular machine: that is a
<Term id="gguf">GGUF</Term> file for llama.cpp.

At work you met ONNX and llama.cpp side by side. This lesson explains what each file actually holds, opens a
GGUF file byte by byte, and shows the commands that turn a Hugging Face model into a quantized GGUF.

</Section>

<Section kind="technical" title="What each format stores">

| Format | Contains | Needs to run it | Typical runtime |
| ------ | -------- | --------------- | --------------- |
| PyTorch `.pt` / `.bin` | Weights, pickled (can execute code when loaded) | The model's Python code | PyTorch |
| safetensors | Named tensors and a JSON header, nothing executable | The model's code and config | PyTorch, Transformers, vLLM |
| ONNX `.onnx` | The graph of operators (opset versioned) and the weights | Any ONNX runtime | ONNX Runtime, TensorRT, Triton |
| GGUF `.gguf` | Metadata (architecture, hyperparameters, tokenizer, chat template) and tensors, often quantized | llama.cpp's implementation of that architecture | llama.cpp, Ollama, LM Studio |

**ONNX** describes a model as a graph: nodes are operators such as `MatMul` or `Softmax` from a versioned
*opset*, edges are tensors. A runtime can optimize and run the graph on CPUs, GPUs or other accelerators without
Python. It suits vision, tabular and encoder models best; the
[ONNX lesson](#/learn/inference/runtimes/onnx-serving) exports one and applies its graph optimizations.
Generating text with a large decoder model through ONNX is possible but needs extra machinery for the KV cache,
which is why LLM serving mostly uses dedicated engines.

**GGUF** works the other way round: it does *not* store the graph. llama.cpp has its own C++ implementation of
each supported architecture (llama, qwen2, gemma, phi3, …) and reads only the settings and tensors. A GGUF file
is laid out as:

1. **Header**: the magic bytes `GGUF`, the version (3), the number of tensors and of metadata pairs.
2. **Metadata**: key-value pairs, each a string key, a type code and a value: `general.architecture`, the layer
   count, head counts, the full tokenizer vocabulary, the chat template.
3. **Tensor infos**: for each tensor its name, its dimensions, its type (F32, Q8_0, Q4_K, …) and its offset.
4. **Padding** to the <Term id="tensor-alignment">alignment</Term> (32 bytes unless `general.alignment` says
   otherwise), then the **tensor data**, each tensor aligned too.

All numbers are little-endian. Because the data is aligned and stored as the runtime uses it, llama.cpp can
memory-map the file and start without copying the weights.

<Section kind="experiment" title="Read the file yourself">

- Select **kv general.architecture**. Its 44 bytes are an 8-byte key length (20), the 20 bytes of
  `general.architecture`, the type code 8 (string), an 8-byte value length (4) and `demo`.
- Select **tensor_info proj.weight**. The dims read `[32, 1]`: ggml lists the innermost dimension first, the
  reverse of NumPy's shape `(1, 32)`. Type 8 is Q8_0. Offset 32 means 32 bytes after the start of the data section.
- Select **padding**: the header ends at byte 235, so 21 zero bytes bring the data section to 256.
- Select **data proj.weight**: 34 bytes at 288. The first two (`29 15`) are the float16 scale, 0.0012598; the
  next 32 are the signed 8-bit integers, starting with `81` (−127).

<Section kind="practice" title="Choosing an export format">

- **LLM on laptops, desktops, Apple Silicon or CPU servers**: GGUF, quantized (Q4_K_M or Q8_0), with llama.cpp
  or Ollama.
- **LLM on GPU servers**: keep safetensors (BF16, or AWQ/GPTQ/FP8 quantized) and serve with vLLM, SGLang or
  TensorRT-LLM.
- **Vision, tabular, speech, embedding models**: ONNX, run with ONNX Runtime (CPU or GPU) or Triton; check the
  opset your runtime supports.
- **Anywhere**: never load pickle files from sources you do not trust; prefer safetensors or GGUF.
- Record the source model, converter version and quantization type next to the file (a model registry entry or
  the GGUF metadata), so you can rebuild it.

</Section>

<Section kind="summary">

- safetensors stores tensors; ONNX stores the graph and the tensors; GGUF stores settings, tokenizer and
  (quantized) tensors for llama.cpp, which implements the graph itself.
- A GGUF file is a header, typed key-value metadata, tensor descriptions, padding to 32 bytes and aligned data,
  all little-endian, so it can be memory-mapped.
- Hugging Face to GGUF: `convert_hf_to_gguf.py` to BF16, then `llama-quantize` to the type you chose.
