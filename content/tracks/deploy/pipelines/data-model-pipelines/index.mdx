<Section kind="intuition" title="An assembly line with a receipt for every part">

Training a model once in a notebook is a craft. Doing it every week, for a team, with new data each time, needs
an assembly line: an <Term id="ml-workflow-pipeline">ML pipeline</Term>. Each station (a *step*) takes parts from
the station before, does one job, and puts its output on the shelf with a label. Those labelled outputs are
<Term id="pipeline-artifact">artifacts</Term>: a dataset snapshot, a feature table, a model file, a metrics
report.

Two things make the line worth building. If you change one station, the stations before it do not need to
work again: their parts are still on the shelf. That is the <Term id="step-cache">step cache</Term>. And every
model leaving the line carries a receipt saying which data, code and settings made it. That receipt is
<Term id="data-lineage">lineage</Term>, and the shop window where finished models wait is the
<Term id="model-registry">model registry</Term>.

At work you met these as Kubeflow, Argo and MLflow. This lesson builds the idea from scratch, then runs the same
pipeline in Kubeflow Pipelines and registers its models in MLflow.

</Section>

<Section kind="technical" title="Steps, artifacts, cache keys and gates">

A typical training pipeline has these steps:

| Step | Reads | Writes |
| ---- | ----- | ------ |
| ingest | a data source and a version or date | a raw dataset snapshot |
| validate | the snapshot | the same rows, or a failure if the schema or ranges are wrong |
| features | validated rows and the feature code | a feature table |
| train | the feature table and hyperparameters | a model file |
| evaluate | the model and a fixed test set | metrics |
| register | the model and its metrics | a new registry version, if the gate passes |

Each step runs in its own container and passes only artifacts and small parameters to the next. The
orchestrator (Kubeflow Pipelines, Argo Workflows, Airflow, Vertex AI Pipelines, SageMaker Pipelines) reads the
graph, starts containers in order, stores every artifact and records what fed what. The
[orchestration lesson](#/learn/data/orchestration/dags-retries) covers the scheduling side: DAGs, retries,
backfills.

**Caching.** Before running a step, the orchestrator computes a *cache key*: a hash of everything that could
change the step’s output. That means the step’s code or image, its parameters, and the keys (or
<Term id="content-hash">content hashes</Term>) of its input artifacts. If an earlier run stored an output under the
same key, the step is skipped and that output reused. Because each key includes its inputs’ keys, a change
re-runs that step and everything downstream, and nothing upstream.

**The gate.** The last step decides whether the new model may replace the one in production. A
<Term id="release-gate">release gate</Term> agreed in advance is usually two checks: an absolute floor (accuracy
at least 0.95, latency under a budget) and a comparison with the current production model on the same test set.

**The registry** keeps every registered version with a link to the run that made it: parameters, data version,
metrics, code commit. Serving loads a name such as `models:/digits@production`, so promoting or rolling back is
moving that alias, not copying files.

<Callout kind="simplification">
  Our cache keys use FNV-1a, a 32-bit hash short enough to read; orchestrators use SHA-256. Real gates often add
  per-slice checks (accuracy on each class or customer group), not just one overall number.
</Callout>

</Section>

<Section kind="mistakes" title="Pipeline mistakes">

<CommonMistake
  title="Reading “latest” data in a cached step"
  wrong={'@dsl.component\ndef ingest(data: Output[Dataset]):\n    urllib.request.urlretrieve("https://example.com/sales/latest.csv", data.path)'}
  error="(no error) the run succeeds with yesterday’s data, because ingest’s cache key did not change"
  cause="The cache key covers the step’s spec and inputs, not what a URL returns. With no parameters, every day looks identical."
  fix={'@dsl.component\ndef ingest(day: str, data: Output[Dataset]):\n    urllib.request.urlretrieve(f"https://example.com/sales/{day}.csv", data.path)'}
/>

<CommonMistake
  title="Comparing with production on a different test set"
  wrong={'acc = model.score(X_test_new, y_test_new)   # new split this run\nif acc > production_accuracy_from_last_month: promote()'}
  error="(no error) a model can look better only because this month’s test set is easier"
  cause="Two accuracies are only comparable on the same data. A fresh random split changes the score by a point or more on small sets."
  fix={'# Keep a fixed, versioned test set, and re-score production on it in the same run\nacc_new, acc_prod = new.score(X_fix, y_fix), prod.score(X_fix, y_fix)'}
/>

<Section kind="practice" title="Pipelines in practice">

- **Version inputs explicitly**: pass a data version, date or content hash as a parameter so caching and lineage
  both work.
- **Pin images and packages** (`scikit-learn==1.9.1`): a new library version changes the output, and should
  change the cache key.
- **Make the gate code, not a meeting**: thresholds in the pipeline, reviewed like any other change.
- **Keep every version** in the registry and serve through an alias; rollbacks become a one-line change.
- **Choosing tools**: Kubeflow Pipelines if you already run Kubernetes and want ML artifacts and caching built in;
  Argo Workflows for general container DAGs (KFP runs on top of it); Airflow or Dagster when the team already
  uses them for data; MLflow for tracking and the registry alongside any of these.

</Section>

<Section kind="summary">

- A pipeline is steps in containers passing versioned artifacts; the orchestrator runs the graph and records
  lineage.
- A step’s cache key hashes its code, parameters and inputs’ keys, so a change re-runs that step and everything
  downstream, and nothing upstream.
- A release gate checks an absolute floor and beats production on the same test set; the registry versions models
  and serving follows an alias.
